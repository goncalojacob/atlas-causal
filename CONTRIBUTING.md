# Contributing

**Contributions are not yet open.** The schema is still being tested against
the atlas's first period, and migrating a hundred contributors' records is far
harder than migrating your own — so the pipeline below is built and tested
first, and announced afterwards. Issues filed now are for the people building
it. When it opens, this is how it will work.

`about.html` is the same thing for readers; this file is for people reading the
repository. `ARCHITECTURE.md` is the structure, `CONTEXT.md` the reasoning,
`STATUS.md` where the project stands today.

## The flow

1. **Build a bundle in the form.** Open `contribute.html` (locally:
   `python3 -m http.server 8000`, then <http://localhost:8000/contribute.html>).
   A bundle is one contribution: an event, the edges that connect it, and any
   source not already in the bibliography. They travel together because an edge
   whose `from` has not been merged yet does not validate — one issue, one
   branch, one pull request.
2. **The form validates before you send.** It loads the atlas's index and runs
   the same validator CI runs: references resolve, the arrow of time holds, a
   `consensus` edge really has two sources by different authors, a `disputed`
   one really carries its dispute. The submit control stays disabled until it
   all passes and every event and edge cites a source. If the form says a
   near-identical title already exists, look at it before continuing: two
   records for the same thing is the one mistake nothing downstream undoes.
3. **File one issue.** The form copies the bundle JSON to your clipboard and
   opens the `Contribution` template with it filled in — or, when the bundle is
   longer than a URL can carry, opens the template empty for you to paste. The
   template asks you to confirm the CC BY-SA 4.0 grant, that the text is your
   own, and that you have consulted the sources.
4. **A maintainer reads it.** The `contribution` label is applied
   automatically and triggers nothing. Only the `accepted` label — which only
   someone with write access can apply — starts
   `.github/workflows/contribution.yml`. That is the spam gate.
5. **The Action writes the records** with `tools/bundle-to-files.mjs`, runs the
   validator and the tests, opens a branch `contribution/<issue>` and a pull
   request, and comments the link back on the issue. If validation fails it
   comments the errors instead and nothing is written. Your GitHub account
   becomes `authors[].github` on every record in the bundle; the commit is
   authored by you.
6. **A person reviews and merges**, against the checklist below. After the
   merge, one job on `main` rebuilds `data/index/` and deploys. Records are
   never deleted: a wrong one becomes a tombstone that still resolves its old
   URL.

A **correction** is the same path with the `Correction` template: paste the
whole record, keeping the id it already has. The Action replaces the file and
appends you to `authors`, keeping the original `created` date and setting
`revised`.

## The review checklist — the part no tool does

The validator can prove that a record is well-formed and that its references
resolve. It cannot read. For every record touched:

- The sources exist, are locatable by the identifier given, and actually
  support the claim.
- The explanation argues rather than asserts.
- The confidence is honest: `consensus` has two independent sources that really
  agree; a `disputed` edge names real opponents in `dispute.text` and cites them
  in `dispute.sources`.
- The edge type is the right one of the five, not the nearest one.
- Dates are checked against the source; `date` is as the source gives it, and
  `calendar` is right where it matters.
- Not a duplicate of an existing record under another transliteration; titles
  and aliases were searched.
- Every word of `summary`, `explanation` and `dispute.text` was written by a
  person. Text generated by a language model is not accepted, in any form, as
  a draft or otherwise.

## The record format

One JSON file per record, under `data/events/`, `data/edges/`, `data/actors/`,
`data/sources/` or `data/presences/`; the id is the file name. The schemas in `schema/v1/` and
`schema/common/` are authoritative — what follows is a synthetic example, of
the kind that lives in `tests/fixtures/`, not a historical claim.

```json
{
  "schema": 1,
  "id": "fixture-event-a",
  "kind": "event",
  "status": "active",
  "supersededBy": null,
  "aliases": [],
  "authors": [{ "name": "A Contributor", "github": "a-contributor" }],
  "license": "CC-BY-SA-4.0",
  "created": "2026-09-01",
  "revised": null,
  "sources": [{ "source": "fixture-source-1", "locator": "ch. 2" }],
  "title": "Fixture event A",
  "summary": "A synthetic event, invented to exercise the interface.",
  "when": { "start": 1400, "end": 1400, "date": "1400-01-02", "calendar": "julian" },
  "where": { "lon": 1.5, "lat": 2.5, "precision": "city", "label": "Fixture place" },
  "region": null,
  "actors": [{ "actor": "fixture-actor-one", "role": "leader" }]
}
```

An edge is the same envelope plus the argument, and its id is derived from its
own fields — `from--to--type` — so the same argument cannot be filed twice:

```json
{
  "schema": 1,
  "id": "fixture-event-a--fixture-event-b--caused",
  "kind": "edge",
  "status": "active",
  "supersededBy": null,
  "aliases": [],
  "authors": [{ "name": "A Contributor", "github": "a-contributor" }],
  "license": "CC-BY-SA-4.0",
  "created": "2026-09-01",
  "revised": null,
  "sources": [{ "source": "fixture-source-1", "locator": "pp. 40-42" }],
  "from": "fixture-event-a",
  "to": "fixture-event-b",
  "type": "caused",
  "confidence": "disputed",
  "explanation": "Why the first event brought about the second, argued rather than asserted.",
  "dispute": {
    "text": "Who disagrees with this link, and on what grounds.",
    "sources": [{ "source": "fixture-source-2", "locator": "ch. 7" }]
  }
}
```

An actor — a person, a polity, an institution or a people — is the same
envelope again, and is reached only through the events that name it:

```json
{
  "schema": 1,
  "id": "fixture-actor-one",
  "kind": "actor",
  "status": "active",
  "supersededBy": null,
  "aliases": [],
  "authors": [{ "name": "A Contributor", "github": "a-contributor" }],
  "license": "CC-BY-SA-4.0",
  "created": "2026-09-01",
  "revised": null,
  "sources": [{ "source": "fixture-source-1", "locator": "ch. 1" }],
  "actorType": "person",
  "names": ["Fixture Actor One", "Fixture the Elder"],
  "summary": "A synthetic person, invented to exercise the interface.",
  "when": { "start": 1180, "end": 1240 },
  "where": { "lon": 1.5, "lat": 2.5, "precision": "city", "label": "Fixture place" }
}
```

Notes that catch people out:

- **Years are integers**, negative for BCE, and there is no year 0. `date` is
  display-only, recorded exactly as the source gives it. A bound may be a range,
  `{ "min": 1400, "max": 1450 }`, and `"end": null` means ongoing.
- **`where` is optional.** A long process with no honest point is a
  timeline-only record, not a dot in the ocean — but then `region` is required.
- **`region` is normally `null`.** The timeline lane is derived from the
  coordinates at index time. Set it only when the derivation would be wrong.
- **`authors`, `created` and `revised` are set by the Action**, not by you.
  Whatever the form puts there is replaced.
- **`actors` names the actors *of* the event**, not everyone alive at the
  time, each with the role it played in it. Roles are free text for now —
  `leader`, `signatory`, `deposed` — compared lowercased and trimmed, so the
  same actor may appear twice in one event only under different roles. Every
  id must resolve to an active actor record.
- **An actor has no lane.** It is never put on the timeline on its own, so
  unlike an event it needs no `region` when it has no `where`. Its `names`
  list must not be empty; `names[0]` is the display name and the rest are
  variants, former names and acronyms, which is what search will use.
- **An actor cites a source too**, like every other node.

## Territories, and the licence they carry

`data/presences/` says who held which ground and when, and
`data/geo/presences/` holds the outlines. Both were imported from
[CShapes 2.0](https://icr.ethz.ch/data/cshapes/) by
`tools/import/cshapes.mjs`, and both are **CC BY-NC-SA 4.0**, not the CC BY-SA
4.0 of everything else under `data/`. So are the actor records the import
created — they live in `data/actors/` beside the hand-written ones and are
told apart by their `authors`, which name the import, and by their `license`.
The validator enforces that: only an import listed in `IMPORT_AUTHORS`
(`src/validate/rules.js`) may put the NC-SA licence on an actor.

Practically, for a contributor: **do not copy anything out of a presence
record, an imported actor record or a geometry shard into a record you are
writing.** The two licences are not compatible in either direction, and a
non-commercial clause cannot be undone once it is in a CC BY-SA file. Writing
a presence of your own is fine — set `license` to `CC-BY-SA-4.0`, cite your
own source, and give it its own geometry.

The import owns its files and nothing else: it refuses to overwrite a record
whose `authors` do not name it, and re-running it changes nothing. If a
CShapes entity ever wants an id that a hand-written record already has, the
tool stops and says so; the fix is an entry in the mapping file below, never
an overwrite.

### Correcting a territory

Which actor a territory belongs to is **data, not code**:
`data/imports/cshapes-actors.json`. Correcting it is an ordinary pull request
against that one file — you never touch `tools/`, and you never edit a
presence record or an outline by hand.

The file is keyed by the source's own entity code (for CShapes the
Gleditsch–Ward code, so an entity the dataset renames still lands on the right
record). One entry looks like this:

```json
"750": {
  "actor": "british-india",
  "names": ["British India", "India (British)"],
  "splits": [{ "from": "1947-08-15", "actor": "republic-of-india" }],
  "note": "why the mapping is what it is"
}
```

- **`actor`** is the actor the code's ground belongs to. If a record of that
  id already exists it is reused untouched, whoever wrote it; if not, the
  import writes one from the source's own fields.
- **`names`** are the names to give an actor the import creates, for when the
  source's name is wrong for the period — CShapes calls entity 750 "India"
  from 1886, colony and republic alike. `names[0]` is the display name.
  Ignored for an actor that already exists.
- **`splits`** are for a code that is more than one actor over its life. Each
  split cuts the code's outlines by date: everything from `from` onwards
  belongs to that split's actor, until the next split. The date must be one
  the source itself draws — the day after some feature's end — and the import
  refuses anything else, naming the boundaries it does have.
- **`note`** is for whoever reads the file next.

A code with no entry gets an actor derived from its own name. Which codes
probably want one is in [`docs/cshapes-entities.md`](docs/cshapes-entities.md),
regenerated by `--report`: every entity the source gives both as somebody's
dependency and as its own state.

`node tools/validate.mjs` checks the file — shape, slugs, split dates in
order, a split's actor not the entry's own. Whether a code exists in the
source at all is checked when the import runs, which is the only place that
can know. **A maintainer then re-runs the import** and commits what it writes:

```bash
node tools/import/cshapes.mjs --source cshapes_2_gw.topojson --report
node tools/build-index.mjs
```

## Working on the code

```bash
node tools/validate.mjs            # schemas, cross-record rules, region derivation
node --test                        # every test under tests/
python3 -m http.server 8000        # then http://localhost:8000/ — add ?fixtures=1
node tools/build-index.mjs         # after changing anything under data/
node tools/import/cshapes.mjs --source cshapes_2_gw.topojson   # territories; rarely
```

Both commands must pass before a pull request is ready. There are no runtime
dependencies, no build step, no map library and no CDN, and pull requests never
touch `data/index/` — `main` owns it.

## For maintainers

- **The `accepted` label is the trigger.** Read the issue first. A label
  already on the issue does not fire the workflow again: remove it and apply it
  again to retry.
- **`CONTRIBUTION_PAT`** is the repository secret `contribution.yml` needs: a
  fine-grained personal access token on this repository with *Contents:
  read and write* and *Pull requests: read and write*. It exists because a pull
  request opened with `GITHUB_TOKEN` starts no workflows, so the contribution
  PR would arrive with no CI at all. Without the secret the workflow stops at
  its first step with a message saying so.
- **PAT expiry: _not yet created — fill in the date when you make it_.** Renew
  it before then; the failure mode is a contribution that stops halfway with a
  403.
