# Atlas causal — review as a reader (22 September 2026)

Reviewed from branch `m0` of /home/gjacob/atlas-causal (live site confirmed identical: `index.html` on
goncalojacob.github.io/atlas-causal matches `m0` byte for byte; the live manifest says 819 events,

## 1. The graph at rest is a tangle a visitor cannot read — blocks the demo

**Seen:** `m76-graph.png` and the owner's own `owner-2026-09-21-graph.png`. Some two hundred
unlabelled circles, most stacked in one column at 1900–2000, crossed by dashed and solid lines in
five styles; a dozen labels, several truncated (“The Atlantic slave trade to Braz…”, “Portugal
adopts the eu…”). `m81-graph-war.png` shows the M81 stretch works once an umbrella is open (World
War II reads well, one label per node), but the first thing a visitor sees on the Graph tab is
still the resting tangle. On a phone (`m77-graph-phone.png`) the labels are about 4 px tall and the
LINKS legend covers half the picture.
**Where:** `src/graph-view/graph-view.js` (resting layout); `src/graph-filters.js:36` (“draws two
links or more”).
**Fix:** at rest draw only main events (M65) with a label on every drawn node, stretch time
horizontally by default so the 20th century gets the width its density needs (the M81 stretch, but
without waiting for a click), and hide labels only when two collide. Make the LINKS key a
collapsed button on a phone.

## 2. Every screen tells a funder that nobody has checked anything — blocks the demo

**Seen:** the masthead reads “0 of 229 read” on every desktop screenshot (`m75-map.png`,
`m76-graph.png`, `m77-timeline.png`, `m80-edge-chosen.png` “0 of 245 read”); every card says

**Where:** `src/window-control.js:82` (`.window-read`), `src/standing.js`, `src/panel/panel.js:437`,
`src/intro.js` (`authorsLine`), `data/narratives/*.json` `authors[0].name`.

## 3. The site never says in plain words what it is — blocks the demo

## 1. The map is drawn while hidden and not drawn again when it comes back

**Severity: bug.** `src/map/map.js` 853–870 (the ResizeObserver), with
`src/main.js` 196 and 296 (subscription order) and `src/map/map.js` 314–321
(`visibleBox`).

What happens: the map subscribes to the store inside `createMap` (main.js
196 → map.js 875), *before* `showView` subscribes (main.js 296). Listeners
run in insertion order, so on `state.set({ view: 'map' })` the map renders
while its pane is still `hidden`; `getScreenCTM()` is null on a hidden
element, `visibleBox()` answers the nominal 960×540 box, and the render key
(map.js 546–548) is stamped with that box — marks in the letterbox margins
are culled (`layers/events.js` 396–397) and the label round is run for the
wrong rectangle. `showView` then unhides the pane and the ResizeObserver
fires, but `last` still holds the size the pane had *before* it was hidden
(the observer returned early at 863 without updating it), so `now === last`
and it returns without rendering (865). The comment at 856–862 says `last`
is "deliberately left alone, so the size it comes back at is a change" — the
opposite is true. The same state change that arrived while the graph was up
(any click on the graph selects, which notifies the hidden map) leaves the
map showing a picture culled and labelled for a box it is not showing until
the next pan, wheel or state change. The graph does not have this fault
because its observer keys on `clientWidth×clientHeight`, which is `0x0`
while hidden (graph-view.js 1267–1270); the timeline redraws unconditionally
a frame later (timeline.js 805–830).

Fix: in the map's observer, when the rect measures nothing set `last = ''`
before returning, so the size it comes back at is a change; or have
`showView` call `map.render(s, { force: true })` after unhiding. Changes
nothing the atlas says.

## 2. The band's profile and the masthead's counts go stale when a lens's late files land

**Severity: bug.** `src/main.js` 101–106 (`remeasure`), 158–162 and 322–327
(what is redrawn on arrival), 236 and 244 (return values discarded);
`src/map-band.js` 185–190 (render key); `src/window-control.js` 162–164.

What happens: `profileEvents` (window-band.js 81–85) is `shown ∩ lensView.kept`,
and `lensView`'s answer changes after the state does — when the grounds and
territories files land for an actor lens (lens.js 555, the stamp), when a
source's citers land, and when a narrative's steps arrive with their century.
`main.js` knows this and forces the three views, the panel and the chips to
redraw (158–162, 322–327). It never tells the band on the map or the masthead
control: `createMapBand` and `createWindowControl` return `render` functions
that main.js drops on the floor (244, 236), `remeasure` reaches only map,
timeline and graph (101–106), and both controls subscribe to the store alone.
The band's key is `renderKey(s, width)` with — deliberately, 181–184 — no
shard count and no lens stamp, so when the file lands and nothing in the
state has moved the key equals `drawnFor` and it returns. Net effect: open a
CShapes polity (350 of the 412 actors have events only by ground), and the
band the owner asked to "follow the selection" (M76) keeps the profile of the
`actors`-named events alone — often nothing — until the reader's next drag or
click; open a narrative from a link and the profile stays the resting
picture's for as long as the narrative's shard takes. The masthead's "N of M
read" (and the count, when a box is on) has the same hole via `workingSet`.

Fix: keep the two return values in main.js and call their `render(s, { force:
true })` from the same two places the views are forced (and `remeasure`), and
put `shardsArrived(atlas)` into the band's key as every view's key carries it.
Changes nothing the atlas says.

## 3. On the graph the masthead count counts the map's box and ignores the degree floor

**Severity: weakness (the count must say what it counts).**
`src/window-control.js` 105–137 and 145–147; `src/graph-view/arrangement.js`
133–154 (no `bbox`), 116–123 (`organises`); `src/state.js` 56–69.

What happens: the count is computed from `bandEvents` narrowed by `s.bbox`
(127–134) whatever `s.view` is. The graph never reads `bbox` (M77 removed even
the note about it, graph-view.js 744–752) and applies the degree floor that no
other view applies (arrangement.js 140). So on `?view=graph` with a box left
over from the map, the masthead reads "N main events of 582 in view" about a
rectangle of the *map*, while the graph draws every main event that organises
two links — today 154 of 245 — with no box at all. Two numbers about two
different pictures in one line, which is exactly the fault M80 was written to
end. Note also that the count is only shown at all while `s.bbox` is set
(145), i.e. after the reader has moved the map: at first paint nobody is told
the picture is 245 of 582.

Fix: make `countInView` view-aware — on the graph, count what
`arrangementOf(atlas, s, …).events` holds and ignore `bbox`; on the timeline
and map keep the box. Consider showing the resting sentence even with no box,
since it is the sentence that answers "I still only see 252 events". Changes
nothing the atlas says.

## 4. Opening an umbrella whose years lie outside the window shows its children on the graph only

**Severity: weakness (reader trip; the owner's want "narrows all three
views to it and its children").** `src/map/layers/events.js` 364–374;
`src/timeline.js` 569–578; `src/emphasis.js` 195–204 (`heldSet` without
`lens`); `src/chain.js` 83–94 (`walkOrSelect` never moves the window);
`src/util/window.js` 59–66 (`MARGIN_YEARS = 50`).

What happens: the map draws an event only if it overlaps the window, the
window ± 50 years, or is in `kept = heldSet(working, { reachable: true })`
(map.js 651); the timeline makes a bar of the same set and a two-pixel stub of
everything else (timeline.js 574–578, 682–697). `heldSet` without `lens:
true` holds the selected event, the walk, the consequences, the actor's and
the narrative's events — never the lens's own children. So a reader on the
graph (unwindowed since M76, arrangement.js 141–154) who opens the Thirty
Years' War while the atlas opened on its busiest century (`opensOn`, data.js
285) gets, on the map, one faded mark for the war and none of its parts, and
on the timeline one faded bar and a row of ticks. Nothing moves the window on
a click — only the search box (search-box.js 158–162) and the card's "map at"
do. The band's profile does show where the children are (finding 2 aside), so
the reader can drag towards them, but the promise M65/M79 make is not kept on
two of the three pictures.

Fix: when a selection sets a lens (lens.js 465–467), widen the window to hold
the lens's own span the way `windowAt` does for a search hit — or, less
intrusively, pass `heldSet(working, { lens: true, reachable: true })` to the
map's `kept` and the timeline's `held` so a lens's children are bars and marks
wherever they fall, faded outside the band as the selected event already is.
Changes nothing the atlas says.

## 5. A graph node cannot be reached from the keyboard; a line can

**Severity: bug (accessibility).** `src/graph-view/graph-view.js` 1056–1058
(node), 1020–1026 (stack), 983–985 and 678–684 (lines get `tabindex`, `role`
and the keydown); `tests/keyboard-browser.test.mjs` covers the map only.

What happens: M63 made every mark on the map a control (`data-mark`,
`tabindex="0"`, `role="button"`, Enter/Space — layers/events.js 321–324,
198–204) and M80 gave the graph's single-link lines the same (983–985). The
graph's nodes and stacks were never given it: a `<circle>` with `data-id` and
no `tabindex` is unreachable by Tab, and the only keydown handler on the root
answers `[data-edge]` (680). A keyboard reader can open a connection on the
graph and cannot open either of its ends, nor any event at all.

Fix: give a node of one the control attributes a map mark has (aria-label =
the title already computed at 1049–1050) and a stack the same with its
`+N` title, extend the keydown at 678 to `[data-id], [data-stack]`, and
remember/restore the focused id across `replaceChildren` as `focusedEdgeId`
already does for lines (721–734). Changes nothing the atlas says.

## 6. Choosing a connection while reading a narrative opens nothing and writes nothing

**Severity: bug.** `src/narrative-mode.js` 20 (`LEAVES`) and 66–72;
`src/panel/panel.js` 752–772 (precedence: narrative before edge);
`src/state.js` 356–363 (`formatState` in reading mode writes no `edge`);
`src/graph-view/graph-view.js` 740–742, 949.

What happens: with `?narrative=…&step=n` open, a click on a line (or Enter on
it) does `state.set({ edge })`. Reading mode passes it through (it is not in
`LEAVES`), the graph draws the line `chosen` (949), but the panel shows the
narrative card first (752) and never reaches the edge branch (764), and the
URL in reading mode carries only narrative, step, walk and focus (356–363).
The reader sees a red line, no card, no address, and the next step of the
narrative silently clears it (`closedEdge`, state.js 599–603). The owner's
sentence for M80 — "select a connection the same way I select an event, so I
can check its sources" — fails exactly where the argument is densest.

Fix: decide which it is and do it in one place: either `edge` leaves the
narrative (add it to `LEAVES`, as `selected` does), or the edge card is shown
over the narrative card and `formatState` writes `edge` in reading mode. The
first is one line and consistent with "a reader who clicks a mark has left the
narrative". Changes nothing the atlas says.

## 7. A chosen connection is invisible on the map and the timeline, and on arrival may be in no picture

**Severity: weakness.** `src/map/layers/events.js` 287–301 (only
`consequence` and `chain` lines are drawn); `src/timeline.js` (no notion of
`edge`); `src/lens.js` 489–518 (`keptRegardless` ignores `state.edge`),
87–92 (`restingSet`); `src/graph-view/graph-view.js` 1229–1245 and
`src/graph-view/frame.js` 40–57.

What happens: the map already draws lines for the selected event's
consequences and the walked chain; it draws nothing for `s.edge`, so a reader

## 1. More than half of the active events show the import's placeholder as their summary, while the article lead is already on disk

**Severity:** missing data.
**Measurement:** 316 of 582 active events (54%) carry `summary` = "Wikidata item Qnnn, imported by tools/import/wikidata.mjs. The item's own description reads "…". Everything here is copied…". 9 of them say the item has no description at all; 306 quote a description under two sentences. 313 of the 316 have the English Wikipedia lead cached at a named revision in `tools/import/cache/wikipedia/`; only 45 of those leads are themselves under two sentences. Beside it, 311 active events cite only the `wikidata` source record although their `wikipedia.en` lead is cached with a `revid`. No hand-written summary is under two sentences except 5.
**Examples:** `1893-franco-siamese-crisis`, `shaba-ii`, `british-russian-convention` (placeholder summary, lead cached); `1918-portuguese-presidential-election`, `1919-portuguese-presidential-election`, `1923-portuguese-presidential-election` (item has no description: the card shows nothing about the event).
**Fix:** a pass over the 313: write the cached lead (first two or three sentences, quoted as the source's words) as `summary`, add the `wikipedia-en` citation with the cached revision as locator, add `summary-drafted` to `review.flags` — exactly what the 126 `summary-drafted` records already look like. ## 2. Three quarters of the active events have no place, and the import threw away 221 coordinates it had in hand

**Severity:** pipeline defect + missing data.
**Measurement:** 425 of 582 active events (73%) have `place: null` (416 wikidata, 9 assistant); all 425 carry a Wikidata item. 221 of them have `regionNote` "derived from its own point": the item had a `P625` coordinate, the import used it to derive the lane and wrote no place. 64 more were laned from the seeds table, 0 from a country point. The A9 place pass has not run (`docs/m42-pool.md` has no `## Places (A9)` section). Two defects in the tool ahead of that pass: (a) A9 as written reads `P276`, `P131`, `P17` and never the item's own `P625`, so a battle with its own coordinate would be given its province or country; (b) `placeRecord()` hard-codes `precision: 'point'` for every place it writes, whereas A9 and `src/vocab.js` PRECISIONS want `city` for a settlement, `region` for anything larger, `country` for a state.
**Examples:** `1920-georgian-coup-attempt`, `1948-arab-israeli-war`, `1948-czechoslovak-coup-d-etat` (own point, no place); `2011-bahraini-uprising`, `battle-of-britain`, `treaty-of-lausanne` (placeless with a locatable item).
**Fix:** in the place pass, try the item's own `P625` first (a place record at `precision: point`, labelled from the item's `P276` or the event's title), then A9's chain; make `placeRecord()` take the precision from the class of the item that supplied the point (settlement → `city`, state → `country`, else `region`). Reuse an existing place by `wikidata` before writing one (rule 21 will refuse a second anyway).
**Who settles it:** source (Wikidata `P625` and the class table).

## 3. Seventeen imported intervals contradict the span their own cited article states in its title or first sentence

**Severity:** wrong data.
**Measurement:** `leads.mjs` compared each active event's `when` with any year range in the cached lead's title or first sentence: 29 disagreements, read one by one. 17 are real (the range names the event itself), 3 are borderline (`cuban-revolution` 1959-01-01 for a revolution the article dates from 1952/53; `franco-russian-alliance` 1894 vs "agreements of 1891–94"; `indo-pakistani-war-of-1947-1948` ends 1949-01-01 vs "1947–1948"), 9 are false positives where the range names something else (`peace-of-riga`, `treaty-of-portsmouth`, `mountain-war`…). ## 4. The import writes "ongoing" whenever Wikidata has no end date, and prefers the point in time over the start

**Severity:** pipeline defect (the cause of part of 3).
**Measurement:** `intervalFor('event')` sets `end: null` when the item has neither `P582` nor `P585` — and `end: null` means *ongoing* in `schema/common/interval.json`. 18 active events are open-ended, 16 of them the import's; for `2011-bahraini-uprising` the cached lead says "from 2011 until 2014", so the record asserts something its source denies. The same function takes `from` as `P585 ?? P580 ?? P571`, so an item carrying a point in time beside a start collapses to one day (`insurgency-in-kosovo` 1998-02-28 with `endDate` the same day; `german-revolution-of-1918-1919` 1918-11-04). Nothing on the record says the end was absent rather than open.
**Examples:** `2011-bahraini-uprising` (open; article: 2011–2014), `covid-19-pandemic-in-europe` and `covid-19-pandemic` (open; no source on the record says ongoing), `insurgency-in-kosovo`, `german-revolution-of-1918-1919`.
**Fix:** in `intervalFor`, prefer `P580` over `P585` for `from` and use `P585` only when there is no `P580`; when `P582` is absent and `P580` present, still write `end: null` but add `review.flags: ["end-unstated"]` and let the curation fire read the lead ("since", "present", "ongoing" keep it open; a stated end year closes it). A record whose only date is `P585` is a day, not a span, and should keep `end = start`.
**Who settles it:** source for the fix of each record (the lead); a tool change for the cause.

## 5. Nearly half the active events name no actor, and the import discards the participants it reads

**Who settles it:** rule (the P710→role table, one line from the owner), then source.

## 7. Title collisions: three active events are titled "Afghan Civil War", two "Treaty of London"

**Severity:** wrong data (on the surface) + pipeline defect.
**Measurement:** `titleFor()` takes the Wikidata label, not the sitelink title, so the article's disambiguator is lost: 22 active events have a title equal to their `wikipedia.en` minus a parenthetical. 5 of them collide with another active event's title: `afghan-civil-war` (1989–92), `afghan-civil-war-q1980081` (1992–96), `afghan-civil-war-q12302518` (1996–2001); `treaty-of-london` (1915), `treaty-of-london-q584617` (1913). `idFor()` handles the id by appending the QID, but the title is what every bar carries since M77. No validator rule looks at titles. Same-QID duplicates: 0; same title and start year: 0.
**Examples:** the five above; `battle-of-the-lys-1918` ("Battle of the Lys (1918)"), `black-monday` ("Black Monday (1987)"), `darfur-genocide` ("Darfur genocide (2003–2005)").
**Fix:** in `titleFor()`, when the English label collides with an existing active event's title (or the sitelink title carries a parenthetical the label lacks), use the sitelink title verbatim — it is the record's cited source. A validator warning `title-shared` for two active events with the same folded title, so the five are on the queue now.
**Who settles it:** source (the sitelink title is on the record).

## 8. Umbrellas and edges follow two contradictory rules, and nine warnings can never be cleared

**Severity:** weak rule.
**Measurement:** 58 active events have children. `tests/m42-filing.test.mjs` refuses an edge at either end of any record flagged `m42-umbrella` (8 records, 0 edges among them). The other 50 umbrellas carry 195 edges (64 in, 131 out), and 56 active edges join a parent to its own child (32 `caused`, 9 `enabled`, 8 `precondition-of` parent→child; 3 child→parent) — the whole "causing" its part, which the model calls a display fact and never an argument. The validator has no rule either way. Meanwhile 9 of the 40 `degree-zero` warnings are exactly the edge-less umbrellas (`interwar-period`, `third-portuguese-republic-since-1974`, `scramble-for-africa`, `afghan-conflict`, `arab-spring`, `indochina-wars`, `decolonisation-of-africa`, `nova-republica-brazil-since-1985`, `arab-israeli-conflict`), so the rule warns about the state the test enforces.
**Examples:** `angolan-civil-war--shaba-ii--enabled` (parent→child), `covid-19-pandemic--covid-19-pandemic-in-europe--caused`, `crisis-portugal--troika-bailout-2011--caused`; edge-less umbrellas as above.
**Fix:** one rule in `src/validate/rules.js` instead of a flag-scoped test: either (a) an edge between an event and its own parent is an error (the relation is `parent`), and `degree-zero` skips an event with active children; or (b) umbrellas may argue like any event and the filing test is dropped. Either way the 56 pairs need a decision: keep the edge and drop the `parent`, or the reverse.
**Who settles it:** rule (owner: is a war allowed to "cause" its battle?).

## 9. A quarter of the edges cite only books with no page

**Severity:** missing data.
**Measurement:** 157 of 638 active edges (25%) have no locator on any citation; 187 have at least one citation without one. All 157 are `origin: assistant`, created 2 to 15 September, and cite only book sources (telo-2007 57 citations without locator, rosas-1994 32, ramos-2009 27, macqueen-1997 27, costa-pinto-2003 25…). Every Wikipedia citation on an edge carries a revision (0 without). 17 `consensus` edges rest on Wikipedia plus one book, which rules 9 and 22 allow.
**Examples:** `1911-portuguese-constituent-national-assembly-election--constitution-1911--caused`, `1911-portuguese-presidential-election--pimenta-de-castro-government-1915--enabled`, `1915-portuguese-legislative-election--germany-declares-war-1916--precondition-of`.
**Fix:** a validator warning `citation-without-locator` on an edge whose every citation lacks one (M72 counts it; the queue should show it); the pages themselves cannot come from the record.
**Who settles it:** person (the book), or a run may add a Wikipedia citation at a revision beside the book where the lead states the same link — which does not remove the book's missing page.

## 10. Refused items are retired for good, and their reasons are overwritten on the next run

**Severity:** pipeline defect.
**Measurement:** `advance()` moves the whole batch into `runs.import.done` whether each item was created or refused; `nextBatch()` never offers a done item again. 166 of the 951 seed items are in `done` with no record of any kind carrying their QID (`Q1018557`, `Q2659185` Nine-Power Treaty, `Q3586973`, `Q233737`, `Q208232`…). `import-wikidata.yml` truncates `docs/import-report.md` before every run (`: > docs/import-report.md`), so the report now holds one batch of 13 and the refusal reasons of the 166 are nowhere in the repository. An item refused because its class was not in the table stays refused after somebody adds the class.
**Fix:** keep refused QIDs out of `done` (a `refused: [{qid, why, on}]` list in `wikidata-state.json`, offered again when the class table or the seeds change) and append the report instead of truncating it, or write refusals into the state.
**Who settles it:** tool change; no historical claim involved.

## 11. 198 presences and 14 relations fall outside the dates of the actor they belong to

**Severity:** wrong data.
**Measurement:** 198 active presences on 47 actors are dated entirely before the actor's `when.start` (the validator prints 20 and "178 more"): Historical Basemaps outlines from 1400–1885 were joined (M59) onto CShapes actors whose `when` begins at the dataset's own horizon, 1886 — `ethiopia`, `france`, `portugal` (13 each), `korea` 12, `oman`/`spain` 10. 14 active `succeeded` relations are dated outside an end's life: `senegal-under-france--senegal--succeeded` 1959-04-04 vs `senegal` from 1960; `east-timor-under-portugal--east-timor--succeeded` 1976 vs `east-timor` from 2002 (the successor in 1976 was the Indonesian occupation); `nazi-germany--german-federal-republic--succeeded` dated 1945-05-23 while the FRG's Basic Law and the actor's own record say 1949.
**Fix:** for the 47 actors, `when.start` from `P571` where `--dates` found one (M49 matched 40 with a P571) with `dates-corrected` and the item as locator; where none, the earliest presence's year with a flag saying the start is the dataset's, not a founding. For the 14 relations: the assistant-drafted one is a plain error settled from the FRG record and Wikipedia; the cshapes ones are the split table's dates and need `data/imports/cshapes-actors.json` edited and re-run, never the record.
**Who settles it:** source for the 40 with a P571 and for `nazi-germany--german-federal-republic`; rule for the rest (which date a succession carries when the successor's own record starts later).

## 12. A6's "span and subject" cannot be checked, because nothing on an umbrella says what its subject is

**Severity:** weak rule + missing data.
**Measurement:** `scope` is declared and read by 7 modules and set by no record (the validator says so: `unwritten-field`), so `world-war-i`, `world-war-ii`, `covid-19-pandemic`, `great-depression`, `scramble-for-africa` are drawn as a point in one lane (europe, europe, asia, americas, africa). An umbrella's subject exists only as prose in `regionNote` (12 distinct sentences). With lane as the only proxy: 119 main events are dated inside an umbrella of their lane and not filed, and the proxy is wrong both ways — `estado-novo-1933-1974` "contains" 20 unfiled European main events that are not Portuguese (`1948-czechoslovak-coup-d-etat`, `austrian-state-treaty`…), while 19 filed children sit in another lane than their parent and are right (`treaty-of-portsmouth` in `russo-japanese-war`, `suez-crisis` in `arab-israeli-conflict`). Asia has no period umbrella at all (63 main events; its umbrellas are wars); the Americas have Brazil's regimes only (22 main).
**Examples:** `interwar-period` (subject Europe, in prose only); `estado-novo-1933-1974` (subject Portugal, in prose only); `world-war-ii` (no `scope`).
**Fix:** write the subject on the umbrella as data — `scope: regional|worldwide` plus the lane, or a `subject: { region | actor }` field — so `child-outside-parent` can be joined by `child-outside-subject` and the filing pass can be measured. Set `scope: worldwide` on the world wars and the pandemics from their own description ("global"), and add the regional periods A10 asks for (Latin America, Asia) to the seeds from their Wikipedia articles.
**Who settles it:** rule (the field's shape is the owner's; the values come from the articles).
